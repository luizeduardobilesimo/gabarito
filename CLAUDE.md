# Gabarito — estudo de viabilidade imobiliária

Ferramenta web (arquivo único) para estudos de massa e viabilidade de empreendimentos residenciais verticais: desenha o lote, aplica as regras da prefeitura, mostra o potencial do terreno, otimiza o produto, calcula a viabilidade financeira, faz layout de garagem e pavimento tipo, e simula sol e vento (2D e túnel de vento 3D).

Publicado como Artifact no claude.ai: https://claude.ai/artifact/4wBW5QrbVhLrqDQgtdFE7G

Contexto da conversa original (histórico, decisões e jeito de trabalhar do Luiz): `HANDOFF.md`.

## Regras de trabalho

- Interface e textos sempre em **português do Brasil**. Respostas ao Luiz em português, listas em tópicos (sem tabelas no chat).
- Padrão visual **premium, sóbrio e moderno** (nada grosseiro), com a **identidade da Rixel** (design system do backoffice: `ecossistemarixel/src/app/backoffice.css`). Qualquer controle novo usa os componentes e tokens existentes do `shell.html` — nunca cor ou fonte fixa.
  - DM Sans em tudo (números com `tabular-nums`; nada de fonte monoespaçada, exceto código: `--f-code`). Claro por padrão, escuro de verdade.
  - **Laranja Rixel (`--brand`) só em:** botão primário (`btn pri`: **um por tela, o "Próximo passo" do rodapé**; no corpo das etapas só `.btn`/`.btn.ghost`; exceções: assistente e tela inicial), indicador da etapa/item ativo (filete fino) e indicadores vivos (ponto do `RES`, barra "calculando…", dica do palco, progresso). Seleção e estados ligados usam o neutro `--sel` (grafite no claro, quase branco no escuro).
  - Situações: `--ok/--warn/--bad/--info` com fundo `*-soft` (pílulas, avisos). Desenho técnico: `--d-acc` (azul: pedestres, PCD, seleção no desenho) e `--mark` (âmbar: frente, rampa, pontos) — nunca na interface.
- Mostrar só o que está ativo: configurações de uma visualização aparecem apenas quando ela está ligada.
- **Guia de UX obrigatório: `docs/UX.md` (v3)** — 5 etapas (Terreno · Produto · Viabilidade · Projeto · Entrega), resultado no topo (`RES`), essenciais abertos, demais seções fechadas com resumo (`SEC`, grupos `SECGRP`), avançado em "Mais opções" (`ADV`), explicações no ⓘ (`INFO`/`TERMO` + `src/ui/glossario.js`), sub-abas (`SUBTABS`), rodapé com o "Próximo passo". Metas por tela: campos visíveis Terreno ≤ 9, Produto ≤ 8, Viabilidade › Resultado ≤ 8, demais ≤ 6; painel ≤ 1.400 px; ≤ 8 seções; ≤ 1 `.btn.pri`; cada `data-p` numa tela só (espelhos em `docs/UX-v3.md` §4.6). Nada de parágrafo no corpo. Especificação da reforma: `docs/UX-v3.md`.
- Não editar `index.html` à mão — ele é gerado.

## Build, testes e desenvolvimento (protótipo local)

```
npm install                       # uma vez (vite, vitest, playwright, three, typescript)
npx playwright install chromium-headless-shell   # uma vez, para o teste visual
npm run dev                       # http://localhost:5173 — monta src/ a cada pedido e recarrega ao salvar
npm run bundle                    # src/ → index.html e test.html (mesmo que `python build.py`)
npm run build                     # + cópia em dist/
npm test                          # Vitest: funções puras + estudos de referência (~1 min)
npm run screens -- all            # Playwright: 5 etapas e sub-abas (+ túnel 3D), desktop+celular (folha média e cheia), claro+escuro → shots/
node tools/auditoria-ui.cjs --dup # 11 telas: campos visíveis, seções, .btn.pri, altura e data-p repetidos; linha "Metas" com o que está fora; confere o inventário docs/aud-v2.json (232 caminhos, estado antes da UX v3)
npm run typecheck                 # tsc sobre os scripts globais (arquivos com // @ts-check)
```

- O empacotador é `tools/bundle.mjs` (o `build.py` só o chama; o Vite usa o mesmo). `index.html` é o que se publica; `test.html` tem `<html><body>` para o navegador/Playwright.
- Ordem de concatenação (tudo global, `"use strict"`): núcleo de cálculo `state, hooks, geom, layout, garagem, model, programa, finance, optim, clima` → **`src/calc/*.js`** (alfabética) → núcleo de interface `plan2d, view3d, ui, steps, views, ai, export, wind3d` → **`src/ui/*.js`** (alfabética) → `main`.
- O código de cálculo (núcleo + `src/calc`) vai também como texto em `<script type="text/plain" id="calcSrc">`: é dele que nasce o Web Worker e é ele que os testes carregam no Node (`tests/harness.js`). Por isso **`src/calc` não pode tocar em DOM** no nível superior.
- Bibliotecas: three.js r128 + OrbitControls (jsDelivr) no carregamento; jsPDF, JSZip, pdf.js (cdnjs) e MapLibre (unpkg) sob demanda.
- Testes: `tests/*.test.js` (Vitest). Estudos de referência em `tests/cenarios/*.json` — se uma mudança de número for intencional, `node tools/gera-cenarios.mjs` e confira o diff. Testes de ponta a ponta (todos com `--html <build>/test.html`): `tools/teste-funcional.cjs` (todas as etapas e sub-abas: criar/editar/mover/excluir + Ctrl+Z, contexto OSM pelo fixture, downloads, celular; `--etapas terreno,entorno,regras,produto,viab,projeto,clima,cen,global,celular` — os nomes antigos seguem como grupos de teste), `tools/teste-plataforma.cjs`, `tools/apresentacao.cjs` (`--fase 1,2,3,4`), `tools/teste-entorno.cjs`, `tools/teste-calibracao.cjs`, `tools/teste-alavancas.cjs`, `tools/teste-assistente.cjs`, `tools/teste-inicio.cjs`. Todos usam `tools/pw-comum.cjs` (`prepara`: three.js de node_modules e a fonte DM Sans de um cache local em `node_modules/.cache/gabarito-fontes`, que nunca segura o carregamento; `abre`: `domcontentloaded` + espera do app pronto). Arquivos `teste-funcional`, `teste-plataforma` e `apresentacao` usam CRLF — edite sem converter o fim de linha.
- Git com remoto `origin` (GitHub). Regras para trabalho em paralelo com agentes: `docs/AGENTES.md`. Plano de backend (Supabase): `docs/BACKEND.md` e `docs/supabase/schema.sql`.

### Pontos de extensão (`src/hooks.js`) — recursos novos entram por aqui
- `extendDEF("chave", padrão)` cria `S.chave` com migração. `HOOK.compute` (fim de `compute`; `opt.quick` = otimizador, pule o pesado), `HOOK.finance`, `HOOK.draw2d` (`ctx={W,H,V,mode,m,opt,w2s,s2w}`), `HOOK.draw3d` (`grp`, `m`), `HOOK.pdf` (páginas extras).
- `m.custosExtra.push({k,nome,sistema,valor})` soma à obra (o orçamento agrupa por `sistema`); `m.vgvUnidades` substitui a receita do mix.
- `addCard(etapa,{key,order,sub,when,html,live,after})` = card extra no inspetor; `ACT.x` / `FX.x` = ações e efeitos novos.
- Um `HOOK.compute` registrado em `src/ui/` NÃO roda no Worker — cálculo que muda `m` mora em `src/calc/`.

## Regras do térreo e das garagens

- O núcleo (escada, antecâmara, elevadores, shafts) aparece em todos os andares; em garagens ele vem com o hall dos elevadores (`lobby`, 2,00 m ao longo da frente inteira, onde abrem todas as portas), obstáculo para vagas e carros. A faixa atrás dele até a fachada da torre (`coreFundo`) é depósito no térreo e piso comum nos subsolos/elevadas (`m.obstGar`); rampas, patamares e faixas de acesso nunca passam sobre núcleo, hall ou essa faixa, em nenhum pavimento (`verticalCruza`).
- Rampas são faixas retas. "Retas empilhadas": todas na mesma projeção — em cada subsolo o carro chega pela ponta de dentro e volta à ponta da frente para descer. "Alternadas (tesoura)": duas faixas lado a lado, sentidos opostos, chegada e partida na mesma ponta. Rampas que descem (subsolos) e que sobem (garagens elevadas) ficam em faixas diferentes, lado a lado na entrada. Cada faixa ocupa só os pavimentos que liga.
- Toda ponta de rampa tem patamar plano (5 m; 6,5 m nas alternadas, para o retorno em U) sem vagas, e um portal que precisa estar ligado à circulação. A rampa só começa 5 m depois do alinhamento.
- Subsolos (e garagens elevadas) com o mesmo contorno são resolvidos juntos (`calc/garmod.js`): mesma rede de corredores (módulo 5,0 + 5,5 + 5,0, sem becos > 25 m), mesma malha de pilares; só a ligação às rampas muda. Faixa de pedestres de 1,20 m do hall dos elevadores ao corredor; PCD com faixa de transferência perto do hall. Meta 25–32 m²/vaga; acima disso o pavimento diz o motivo.
- Cada pavimento é conferido numa malha de 0,5 m: o carro (folga de 2,4 m) precisa ir de um portal à frente de cada vaga, com profundidade de manobra livre diante dela; corredores isolados ganham uma passagem (tirando o mínimo de vagas); sobras recebem vagas extras de frente para a circulação.
- Chaves por pavimento em `m.gar`: `s1..sN`, `ter`, `g1..gN`. Marcações manuais usam `<pavimento>:<índice>`.
- Rampa movida à mão (`estudo.rampa`): define a faixa de entrada; as outras ficam ao lado. Vale a mesma regra dura: se ela passar pelo núcleo, a circulação fica inválida com o aviso (testes: `tests/lotepequeno.test.js`, com o lote 25 × 30 de esquina de `tests/fixtures/lote-25x30-esquina.json`).
- Térreo (`calc/comuns.js`): o hall é dimensionado pelo hall social + lazer coberto + apoio do condomínio; clausura e portaria na fachada, ambientes encostados nas paredes (fachada, divisa, núcleo e depósito atrás dele, garagem), vão central como hall e galeria até a porta do elevador de cada torre (rota ≥ 1,20 m, nunca pela faixa de veículos); lixo, gás e medidores no recuo; nada do planejador sobre vaga ou corredor da garagem do térreo.
